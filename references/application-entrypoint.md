# 应用入口与真实运行

影刀有三种容易混淆的执行面，先声明用户要求的级别：

| 执行面 | 典型命令/动作 | 证明的范围 |
| --- | --- | --- |
| 整个应用 | 控制台任务运行 app | 从 startup flow 开始的应用级运行 |
| Studio 当前流程 | `studio app run --flow-id` | 指定 flow；不等于整个应用 |
| 单个 CodeFlow | 调用模块或独立 CodeFlow | 只证明该模块 |

## 运行前入口预检

1. 用当前 CLI 查询 app detail，记录 `appId`、应用名、`startup_flow_id`、版本/同步状态和编辑锁状态。
2. 用 flow list 找到启动流程，再读取其真实内容：可视化流程用 `blocks-list`，CodeFlow 用 `codeflow read` 或应用目录中的源文件。
3. 如果启动流程是可视化流程且区块数为 0，或没有任何调用目标，标记为“结构性空入口”。如果应用说明声称会编排业务，入口与说明不一致时先停止，不要用手工调用内部模块冒充整应用运行。
4. 如果启动流程是 CodeFlow，确认存在严格的 `def main(args):`，并记录它调用的下一跳和输出。

## 运行边界

- 用户要求运行整个应用时，优先使用控制台任务运行 app；不要把 Studio 单 flow 运行或单个 CodeFlow 运行报告为整应用测试。
- 应用正在 Studio 编辑时，先保存，再使用当前版本支持的 sync-close/关闭编辑会话能力释放编辑锁；收到“应用正在编辑”时不要盲目重试。
- 运行结果中的 `success=true`、`run_succeeded=true`、静态错误为 0 或很短的耗时，只能证明任务完成/无运行时错误，不能证明业务执行过。

## 空跑判定与证据

将下列组合判定为疑似空跑并继续查入口，而不是报告成功：任务瞬间完成、日志只有开始/结束、浏览器未打开、输入批次没有 manifest/中间文件、输出目录无变化。记录任务 ID、运行日志、入口区块数和预期副作用。

业务成功还必须有与任务对应的副作用证据，例如批次流程的 manifest、目标 Profile/页面、正确业务表头的导出文件和最终核对结果。文件存在但字段属于另一业务时仍判定失败。

## 全局变量

运行前读取并记录相关全局变量；只修改用户本次任务需要的变量，保存后再运行。报告中列出修改项和保存状态，避免把持久变量变化误报成业务代码修改。
