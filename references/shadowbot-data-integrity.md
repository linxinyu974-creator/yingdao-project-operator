# ShadowBot 数据完整性与错误传播

通过 `user.db3` 或当前 CLI 查询应用名称到 app ID 的映射，再进入对应应用目录。执行数据库脚本时优先使用该应用的 `venv310\Scripts\python.exe`，并显式使用 UTF-8；排查源码时排除 `cef`、`cef_main`、`venv`、`site-packages` 和缓存目录。

先读取实际 schema、索引和写入 SQL。抖音精选流程中，`shops_dy_sub` 仅按 `shops_id` 做全局白名单，不含 `subject_id`；`order_data_day_dy` 的唯一键为 `(subject_id, order_id, data_type)`，同一订单以不同主体写入不会被 `INSERT IGNORE` 消除。分析时输出店铺、日期、主体集合、订单数、行数和写入时间批次。

区分三种动作：报表层按正确归属主体去重；历史记录迁移/归属修复；修改白名单、选择条件或幂等键以防复发。不要用简单 `DISTINCT` 或“保留最新”替代归属判断，也不要在未完成全库扫描时宣称已列出全部受影响店铺。

沿调用链向上追首个错误：数据库连接或认证失败可能返回 `None`，业务模块随后把 `None` 当文件路径传给文件模块，最终在 `os.path.exists` 或 `stat` 处报类型错误。发送文件前强制校验返回值为非空、存在且可读的路径；失败时记录原始数据库错误、查询条件和跳过原因，恢复连接后才重试。

把“现象、已验证根因、实际修复、验证证据、适用边界”分开记录。未运行、未重启或未验证的步骤不得写成已完成；密码、Cookie、验证码和完整账号不得进入日志、skill 或回复。
